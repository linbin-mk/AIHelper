## Context

AIHelper 当前通过 4 个独立 OpenSpec Skill 支持代码开发工作流（探索→提案→实现→归档），但每个 Skill 需要用户通过斜杠命令手动调用，且需理解 proposal/design/specs/tasks 等抽象概念。目标是为非技术用户提供单一入口的向导式体验。

项目已有成熟的 Skill 注册机制（`window.__registerSkill`）、分类系统（通用/业务/产品/开发/测试/其他）和 askUser 询问卡片工具，本设计完全基于现有基础设施，不引入新依赖。

## Goals / Non-Goals

**Goals:**
- 提供一个 "代码大师" Skill（id: `code-master`，分类："开发"），作为代码开发的唯一向导入口
- 通过 askUser 工具实现五阶段向导流程：需求描述 → 方案确认 → 代码实现 → 测试验证 → 归档完成
- 自动调度 openspec CLI 完成底层操作，对用户完全透明
- 支持中途退出和状态恢复

**Non-Goals:**
- 不修改现有 4 个 OpenSpec Skill 的行为
- 不修改 Skill 系统或 askUser 工具的基础实现
- 不提供 GUI 面板以外的交互方式
- 不处理多人协作或分支管理场景

## Decisions

### 1. Skill 定义为纯 Prompt 驱动（无需 JS 代码）

**选择**: Skill 仅包含 SKILL.md 文件（YAML front matter + Markdown prompt），不提供 `index.js`、`getTools()` 或 `getUIDelegate()`。

**原因**: "代码大师"的核心价值在于工作流编排和用户引导，而非自定义工具或 UI。AI 模型通过 prompt 中的工作流指令和现有的 `askUser` 工具即可完成所有交互。现有 openspec-cli 通过 bash 工具调用。

**替代方案**: 编写 JS 实现注册自定义工具（如 `startCodeMaster`）。被拒绝——增加维护复杂度且功能上无增益。

### 2. 五阶段流水线设计

**选择**: 将代码开发分解为 5 个线性阶段，每阶段结束时通过询问卡片获取用户确认后才进入下一阶段。

```
需求描述 ──→ 方案确认 ──→ 代码实现 ──→ 测试验证 ──→ 归档完成
   │            │            │            │            │
   └── 用户补充 ──→ AI生成 ──→ AI编码 ──→ 用户测试 ──→ 自动归档
        需求      提案/方案     与实现        反馈       与总结
```

**原因**: 线性流程降低认知负担，每阶段明确的"确认点"让用户有掌控感。用户可以随时说"取消"退出。

**替代方案**: 非线性 DAG 工作流（允许跳转），被拒绝——对于技术小白用户来说过于复杂。

### 3. askUser 卡片设计策略

**选择**: 每阶段使用不同模式的询问卡片：
- 阶段1（需求描述）：`allowFreeInput: true`，让用户自由描述需求
- 阶段2（方案确认）：`options` 列表 + 确认/修改按钮
- 阶段3（代码实现）：`options: ["开始实现", "我想修改方案"]`
- 阶段4（测试验证）：`options: ["通过，进入下一步", "有问题需要修复", "我想查看代码"]`
- 阶段5（归档完成）：`options: ["确认归档", "暂不归档"]`

**原因**: 每阶段的信息需求不同，卡片模式需匹配用户在该阶段的自然决策方式。

### 4. 进度状态管理

**选择**: 使用 openspec change 目录下的 `.openspec.yaml` 中追加自定义字段跟踪向导进度，不引入额外的状态文件。

**原因**: 复用已有的 change 目录结构，openspec CLI 本身就需要该文件。避免多文件状态不一致的问题。

**替代方案**: 使用单独的状态文件（如 `.code-master-state.json`）。被拒绝——增加文件管理复杂度。

## Risks / Trade-offs

- **[风险] AI 可能不按 prompt 指令严格执行五阶段流程** → 在 prompt 中使用强约束语言（"必须"、"禁止跳过"）并在每阶段输出结构化标记
- **[风险] 用户在阶段3中途退出，change 目录可能残留半成品** → 在 prompt 中提供 "清理" 指令，归档前检查任务完成状态
- **[风险] askUser 卡片交互依赖前端实现，若前端不支持某些模式则降级** → 仅使用已实现的 `options`、`multiSelect`、`allowFreeInput` 三种模式，不使用未验证的参数
