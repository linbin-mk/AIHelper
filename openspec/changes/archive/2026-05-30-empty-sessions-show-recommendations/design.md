## Context

当前欢迎页包含「最近会话」区块，当用户有历史会话时展示最多 3 个最近会话卡片。当无历史会话时，该区块通过 `display: none` 完全隐藏，仅剩简介文字和输入框。新用户首次进入时缺乏可操作的引导入口。

本设计在无历史会话时用预设推荐提示卡片替换隐藏的「最近会话」区域，引导用户快速发起首次对话。

## Goals / Non-Goals

**Goals:**
- 无历史会话时展示 3 个推荐提示卡片，视觉上占据「最近会话」区域的位置
- 推荐卡片可点击，点击后创建新会话并自动发送预设问题文本到输入框（用户可修改后再发送）
- 推荐内容通过 i18n 维护，中英文分别提供
- 复用现有 `.recent-session-card` 样式，保持视觉一致性

**Non-Goals:**
- 不实现动态推荐（基于用户行为或上下文生成）
- 不实现推荐卡片的远程配置或后台管理
- 不修改有历史会话时的行为

## Decisions

### 1. 推荐卡片数据通过 i18n 维护

**决定**: 推荐列表定义为 i18n 键值数组，而非硬编码或独立配置文件。

**理由**: 推荐内容需要中英文双语支持，i18n 是现有的国际化机制。数组结构允许未来方便地增删推荐条目。无需引入额外配置文件。

**替代方案**: 硬编码 HTML — 但中英文切换时需要动态替换文本，复杂度更高。

### 2. 推荐卡片点击行为：填充输入框而非自动发送

**决定**: 点击推荐卡片后，创建新会话（如同点击「+ 新建会话」），并将推荐问题文本填入输入框，让用户自行决定是否发送。

**理由**: 
- 给用户机会修改问题后再发送，避免“不可逆”的感觉
- 与当前「+ 新建会话」的行为一致（清空聊天区 → 欢迎页 → 等待输入）
- 如果直接发送，用户可能觉得突兀

**替代方案**: 直接发送 — 但缺少修改机会，体验较差。

### 3. UI 结构：在 `#welcomeRecentList` 内动态渲染

**决定**: 修改 `renderRecentSessions()` 逻辑，当 `recent.length === 0` 时不隐藏容器，改为渲染推荐卡片 HTML。复用 `.recent-session-card` 样式类。

**理由**: 最小化 DOM 结构变更。`#welcomeRecentList` 和 `#welcomeRecentSessions` 容器已存在，推荐卡片直接插入同一列表元素即可。复用样式减少 CSS 改动。

**替代方案**: 新增独立 DOM 容器 — 但视觉上推荐卡片应和最近会话卡片在同一位置，无需独立容器。

### 4. 推荐卡片视觉区分

**决定**: 推荐卡片使用 `.recent-session-card--recommend` 修饰类添加微弱视觉差异（如左侧彩色竖线、图标前缀或半透明背景），区别于历史会话卡片。

**理由**: 用户需要能区分“这是我的历史会话”和“这是推荐提示”。纯文字差异（标题不同）不够直观。

## Risks / Trade-offs

- [推荐内容不够吸引人] → 推荐内容可随版本迭代更新，i18n 数组易于编辑
- [用户点击推荐后发现不会用] → 文本已填入输入框，用户可以修改或清空，无锁定风险
