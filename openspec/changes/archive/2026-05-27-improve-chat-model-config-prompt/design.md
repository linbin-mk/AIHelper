## Context

当前 `panel.js` 中 `checkConfigAndOpenChat()` 函数在用户点击"AI聊天"Tab 时静默检测模型配置：若三个必填字段（`apiBaseUrl`、`apiKey`、`modelName`）任一为空，则 `switchTab('settings')` 跳转到设置页。同时 `config.js` 保存配置成功后自动 `switchTab('chat')` 跳回。这两个自动跳转对用户来说是**无感知的暗逻辑**，交互不友好。

需要将配置检测时机从 Tab 切换推迟到用户实际尝试使用聊天功能时（输入框获得焦点 / 点击发送），并以可视化的悬浮提示框替代静默跳转。

## Goals / Non-Goals

**Goals:**
- 移除 `checkConfigAndOpenChat()` 的静默跳转逻辑
- 移除 `config.js` 保存成功后的自动跳转
- 在输入框 `focus` 事件和发送按钮 `click` 事件中检测模型配置
- 未配置时展示悬浮提示框，包含说明文字和"前往设置"按钮
- "前往设置"按钮点击后跳转到设置页 > 供应商面板

**Non-Goals:**
- 不改变已配置模型时的任何交互行为
- 不改变设置页的保存逻辑（除了移除自动跳转）
- 不修改模型配置的数据结构和存储方式
- 不添加每隔一段时间重复检测的轮询逻辑

## Decisions

### 决策 1: 检测时机 —— 输入框获焦 + 发送按钮点击

**选择**: 在输入框 `focus` 和发送按钮 `click` 两个事件点做检测。

**备选方案**:
- 仅在 Tab 切换时检测：就是当前方案，已经被否决
- 仅在发送时检测：用户可能输入了很多内容后才发现需要配置，体验略差

**理由**: 在 `focus` 时提前检测，用户第一时间知道需要配置；在 `click` 发送时再次兜底检测，防止用户在获焦后未操作、切换窗口配置了但忘记刷新。两个检测点都使用同一个提示框，不重复弹出。

### 决策 2: 提示框 UI —— 内联悬浮提示而非模态弹窗

```
┌─────────────────────────────────────┐
│  聊天主区域                          │
│                                     │
│  ┌──────────────────────────────┐   │
│  │ ⚠️ 尚未配置大模型            │   │
│  │ 请先前往设置页面配置 API    │   │
│  │ 连接信息以开始 AI 对话       │   │
│  │ [前往设置]                   │   │
│  └──────────────────────────────┘   │
│  ┌──────────────────────────────┐   │
│  │ 输入框 (灰色/禁用状态)        │   │
│  └──────────────────────────────┘   │
└─────────────────────────────────────┘
```

**选择**: 在输入区域上方展示一个内联悬浮提示气泡（绝对定位，`position: absolute`，带箭头指向输入框），背景使用主题的 warning/accent 色。提示框不阻塞页面其他操作，用户可以自由点击其他 Tab。

**备选方案**:
- 模态弹窗（Modal）: 太重，阻断用户操作流
- 顶部 Snackbar/Toast: 位置不够显眼，且和输入框关联性弱
- 纯文字 inline 提示: 可能被忽略

**理由**: 悬浮气泡视觉上靠近输入框，关联性强，且不阻塞用户切换到其他 Tab 做其他事。气泡显示时输入框保持可见但设为 disabled 状态（视觉上提示不可用），光标不会在输入框中闪烁。

### 决策 3: 提示框消除时机

**选择**: 以下任一条件消除提示框：
1. 用户点击"前往设置"按钮
2. 用户点击提示框外部任意位置
3. 用户切换 Tab

**理由**: 给用户充分的消除路径，不强制绑定操作。

### 决策 4: 模型配置检测方式

**选择**: 复用 `loadModelConfig()` 函数（从 `chrome.storage.local` 读取），每次检测时实时加载。

**备选方案**:
- 页面初始化时缓存配置：如果用户在另一个 Tab 中修改了配置，缓存可能过期

**理由**: 检测频率低（仅在用户交互时触发），`chrome.storage.local` 读取足够快，无需额外缓存层。

### 决策 5: 实现位置

**选择**: 提示框逻辑封装在 `panel.js` 中的独立函数，由 `panel.js` 初始化时绑定事件到输入框。`config.js` 仅移除跳转调用。

**理由**: 提示框 UI 的逻辑属于面板级别行为，放在 `panel.js` 中与其他 Tab 切换逻辑在一起。`chat.js` 保持职责单一——处理聊天消息的发送和渲染。

## Risks / Trade-offs

- **[低风险] 用户可能多次看到提示**: 每次 focus 都会检测，如果用户不配置且在几个 Tab 间切换回来再次聚焦，提示会再次出现。这是预期行为，作为温和的催促。
- **[低风险] 输入框 disabled 视觉**: 未配置时输入框设为 disabled，用户可能感到奇怪。通过悬浮提示的文字说明来消除困惑。
- **[无风险] 向后兼容**: 已配置模型的用户不受任何影响，检测通过后直接放行，不产生额外 UI。
