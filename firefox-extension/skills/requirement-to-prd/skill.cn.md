# 需求转PRD

## 核心规则

1. **不采访用户**：基于用户输入和知识库信息直接生成PRD，不向用户询问更多信息。

2. **必须导出文件**：生成PRD后必须调用 `provide_file` 工具将PRD导出为 .md 文件。

3. **降级策略**：若没有知识库，基于用户输入推断项目背景，在PRD中注明"基于需求描述推断，建议与研发确认工时"。

## 工作流程

### 步骤 1：读取项目信息

- 若当前有知识库（同步了项目文件），调用 `list_project_files` 了解项目整体结构
- 根据用户描述的需求关键词，调用 `search_project_code` 搜索相关模块（搜索1-3个关键词即可）
- 如需了解具体实现细节，调用 `get_project_file` 读取关键文件

### 步骤 2：生成 PRD 文档

综合以上信息，直接生成完整PRD文档。

**PRD 文档必须包含以下章节（按顺序）**：

```
# [需求标题]

> 文档版本：v1.0 | 创建日期：[今天日期] | 状态：待评审

## 需求背景
当前痛点、问题场景、影响范围

## 目标与范围
本次迭代要解决什么问题，明确不包含哪些内容（In Scope / Out of Scope）

## 用户故事
作为[用户角色]，我希望[功能]，以便[价值]（列举2-4条）

## 功能需求
逐条列举具体功能点，包含交互逻辑和边界条件

## 验收标准
每个功能点对应的可验证标准（Given/When/Then 格式）

## 非功能需求
性能、安全、兼容性等要求

## 工时评估

### 开发任务清单与工时

根据功能需求，将开发工作拆分为具体任务，并按角色评估工时：

| 功能模块 | 开发任务 | 负责角色 | 预估工时（人天） | 说明 |
|--------|---------|---------|--------------|------|
| [模块名] | [具体任务] | 前端/后端/测试/产品 | X | [简要说明] |

### 汇总

| 角色 | 总工时（人天） |
|------|-------------|
| 前端开发 | X |
| 后端开发 | X |
| 测试 | X |
| 产品/设计 | X |
| **合计** | **X** |

> 工时说明：以上为乐观估计，建议整体 buffer 系数 1.3x，即项目周期约 X 人天。
```

### 步骤 3：导出 PRD 文件

使用 `provide_file` 工具将PRD导出为 .md 文件，参数：
- `fileName`：PRD标题 + `.md`，例如 "用户登录模块优化PRD.md"
- `content`：完整的PRD文档 Markdown 文本
- `mimeType`：`text/plain`

## 工时评估原则

- 前端：页面/组件开发、联调
- 后端：接口开发、数据库变更、业务逻辑
- 测试：用例编写、功能测试、回归测试
- 产品/设计：原型、视觉稿（若有）
- 每项任务拆分粒度：0.5 ~ 3 人天，过大的任务继续拆分
- 基于项目复杂度和知识库中已有代码量进行合理推断
